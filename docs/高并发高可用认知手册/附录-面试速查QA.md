## 一、缓存（6 题）【第01篇】

**Q1. 缓存穿透、击穿、雪崩的区别和解法？** 【第01篇】
口诀先出：穿透是"key 不存在"，击穿是"一个 key 太烫"，雪崩是"一片 key 一起死"。穿透解法：布隆过滤器挡恶意扫描 + 空值缓存兜重复查询；击穿解法：互斥锁重建（要双重检查、锁带超时）或逻辑过期（先返旧值、异步刷新），取舍维度是"这个 key 的旧值能不能用"；雪崩解法：TTL 加随机抖动、错峰预热、多级缓存兜底、熔断降级、Redis 高可用。收尾加分：三者最终都压向 DB，保护 DB 是缓存设计的最高纲领。

**Q2. Cache Aside 为什么是删缓存而不是更新缓存？** 【第01篇】
三条递进：一是懒加载效率——更新完没人读就是白算，删除让下次读自然回填；二是缓存值可能是 join 再聚合的计算结果，"更新缓存"意味着写方也得会算，职责就脏了；三是并发写交错——两个写并发更新缓存，旧值可能后落缓存且活到 TTL 到期，而删除是幂等、无顺序敏感的，下次读回填的一定是新值。

**Q3. 先删缓存还是先更新数据库？** 【第01篇】
标准答案：先更新库，再删缓存。先给对方推演"先删缓存"的失败时序：删完缓存 → 并发读 miss 查到旧值 → 回填旧值 → 库才更新成新值，脏数据活到 TTL。而"先更新库再删缓存"的不一致窗口只在更新库到删缓存之间的毫秒级，还要求恰好此刻有读命中旧值，概率低得多。主动承认它不完美——这是工程成本下概率最优的选择，不是强一致。

**Q4. 怎么保证缓存和数据库的一致性？** 【第01篇】
先泼冷水：引入缓存那一刻就放弃了强一致，能做的只是控制不一致窗口的大小。手段按强度排：Cache Aside 标准模式 → 延迟双删（清掉更新期间被并发读回填的旧值，但延迟时长靠拍脑袋、第二次删除可能失败）→ Canal 订阅 binlog 异步失效（把失效逻辑从业务代码剥离，适合失效点散落在几十处的大系统）。真正强一致的字段（金额、余额）正确姿势是这条链路不走缓存，直接读主库。

**Q5. 热 key 和大 key 怎么处理？** 【第01篇】
热 key 靠监控发现（hotkeys 命令、代理层统计、客户端埋点），处理两手：本地缓存承接（Caffeine 秒级 TTL，消化绝大部分读）+ key 拆分成 N 个副本读写分摊（N 倍存储换 N 倍吞吐），两者常叠加。大 key 的危害三条：Redis 命令执行单线程，HGETALL 或 DEL 一个大 key 会卡住整个实例几十毫秒；高频读打满网卡；集群下造成内存倾斜。处理：value 设上限告警、按字段或时间拆分、UNLINK 异步删除、bigkeys 扫描监控。补一句：生产禁 KEYS，排查用 SCAN。

**Q6. 布隆过滤器原理？为什么有误判？** 【第01篇】
本质是一个位数组 + k 个哈希函数：加入元素时算出 k 个位置全部置 1；查询时 k 个位置只要有任何一位是 0，元素一定不存在，放心拦截；全是 1 则"可能存在"——那些 1 可能是别的元素凑出来的。所以它有误判（false positive）但绝不漏判；标准实现不支持删除（清 0 会误伤共用位的其他元素，要删除用 Cuckoo Filter）；空间效率极高，存一亿个 ID、误判率 1% 大约只需一百多 MB。调参方向：内存和误判率互换，预算内选业务能接受的上限。

## 二、限流与熔断（5 题）【第02篇】【第07篇】

**Q7. 令牌桶和漏桶的区别？** 【第02篇】
考点不是定义，是两种流量整形哲学：漏桶强制匀速出水，突发全被排队抹平——适合下游有硬匀速要求的场景，比如银行通道合同写明每秒最多 50 笔；令牌桶匀速产令牌、用桶容量攒"信用"容忍突发，只约束长期平均速率——通用入口首选，因为真实流量天然是脉冲式的，多数下游怕的是持续超载而不是瞬时冲高。加分句：Nginx 的 limit_req 是漏桶，加 nodelay 后行为更像令牌桶。

**Q8. 接口被刷了怎么办？** 【第02篇】
按防线链从远到近答：一、先靠监控识别是恶意流量还是业务洪峰（QPS 突增、单一 IP/UA 占比异常），这决定后面是"封"还是"扛"；二、CDN 卸载静态资源，WAF 规则拦截、人机验证、IP 封禁；三、网关层按 IP 粗限 + 全局总闸，超量的 429 掉；四、应用层按用户/接口精细限流，贵接口单独收紧，配黑白名单；五、下游已劣化就熔断保护调用链，读接口降级返回缓存快照；六、必须吃掉的写流量进 MQ 削峰，后端匀速消费。一句话版：能封的封，封不掉的分层限，限不住的降级熔断，必须吃的进队列。

**Q9. 集群环境下怎么做全局限流？** 【第02篇】
先指出单机限流的两个漏洞：N 台机器 × 单机阈值 ≠ 全局限值（负载均衡不均，总量会漂移）；用户维度限流直接失灵（同一用户的请求散到各机，单机视角都没超限）。方案：令牌桶状态集中到所有实例共享的 Redis，用 Lua 脚本把"读状态-补令牌-判断-扣减"打包成一个原子操作，消除 check-then-act 竞态——这句话必须脱口而出。工程细节：令牌惰性计算、时间源用 Redis 服务器的 TIME 防时钟漂移。进阶：本地单机限流粗筛 + Redis 精确配额的两级限流，摊薄网络开销。

**Q10. 熔断和降级有什么区别？** 【第07篇】
熔断是自动开关：下游失败率或慢调用比例超阈值就跳闸，请求根本不再发出，保护的是调用方自己不被下游拖死；降级是兜底答案：返回默认值、返回缓存旧数据、关闭非核心功能。两者的关系：降级是熔断和限流共同的善后手段——熔断决定"不再调"，降级决定"给用户看什么"。降级可以由熔断自动触发（Fallback），也可以是人工预案开关（大促时关掉导出、评论），成熟体系两者都要。

**Q11. 熔断器的三态是怎么工作的？** 【第07篇】
Closed 正常放行，后台持续统计；统计窗口内失败率或慢调用比例超阈值（注意有最小请求数门槛，防低流量误熔断）→ Open 跳闸，所有请求快速失败走兜底，进入冷却期给下游恢复机会；冷却到期 → Half-Open，放少量试探请求过去，成功数达标回 Closed，仍失败回 Open 重新冷却。Half-Open 的精妙在于全自动解决"下游到底好没好"的探测，且避免恢复瞬间被全量流量冲垮。必补一句：只看异常率的熔断器挡不住"下游只是变慢"的雪崩，必须有慢调用比例熔断。

## 三、MQ 与异步（5 题）【第03篇】

**Q12. MQ 怎么保证消息不丢？** 【第03篇】
标准答案是三段闭环，缺一不可。生产端：同步发送 + 确认（acks=all / SEND_OK），失败本地重试，重试仍失败落本地消息表 + 告警兜底；Broker 端：刷盘持久化 + 多副本（ISR 内副本都确认写入才算提交）；消费端：先处理业务、成功后再手动确认，失败不确认走递增间隔的重试阶梯，超过上限进死信队列转人工。收束句：消息不丢不是 MQ 产品自带的属性，是三段各自正确配置后涌现出来的系统属性。

**Q13. 怎么处理重复消费？** 【第03篇】
先讲为什么必然重复：at-least-once 是工程现实——ack 丢失重发、rebalance 重新分配、提交位点失败、人为重放，源头堵不死；exactly-once 是有限定边界的能力而非银弹。结论：不要试图让消息不重复，要让重复的消息不造成伤害，这就是幂等。三种落法：唯一约束/去重表（关键点是去重插入和业务写必须在同一个本地事务里）；状态机校验（UPDATE ... WHERE status=前置状态，零额外成本，发票状态流转是天然教材）；业务版本号/递增序号（顺带治乱序）。实战常混用：状态机兜底 + 去重表防无状态消息。

**Q14. 怎么保证消息顺序？** 【第03篇】
先破执念：全局有序基本等于单线程处理，吞吐直接崩盘，业务几乎从不需要它。真实需求永远是"同一业务实体的消息有序"——同一个订单的创建、支付、关闭要有序，不同订单之间无所谓。解法：按实体 key 哈希路由到同一个分区/队列，队列内天然有序（Kafka 按 key 落 partition；RocketMQ 顺序消息 + MessageQueueSelector）。代价要说清：牺牲并发度、有队头阻塞；Broker 宕机切换后顺序可能有短暂破口，强顺序场景要配事后对账兜底。

**Q15. 消息积压了怎么办？** 【第03篇】
先定位三大成因：消费慢（慢 SQL、同步调第三方，最常见，最值得先查）；流量突增；消费者宕机或 rebalance 风暴。处置三板斧按优先序：扩容消费者（上限是分区数，超了干瞪眼，必要时先扩分区）；批量消费 + 排查消费逻辑慢点；极端情况对非关键消息降级跳过快速清积压，保核心消息。比处置更重要的是监控意识：积压量 lag 是 MQ 第一指标，必须有告警阈值——发现堆积的正确路径是监控报警，绝不是业务方打电话来骂。

**Q16. 为什么要用 MQ？什么场景不该用？** 【第03篇】
三大职责先摆：异步化（把不需要立即知道结果的事挪出同步链路，用户感知 RT 变短，但总耗时反而变长）；削峰填谷（队列当水库，洪峰蓄水、匀速消费，省下按峰值扩容 50 倍的钱）；解耦（新增订阅方零改动，代价是链路黑盒化、契约运行期才校验）。再给判断维度：链路中非关键环节多、峰谷比超 5 倍且峰值短、订阅方 ≥ 2 且有增长预期——用 MQ；一对一强依赖返回值、流量平稳的内部系统——同步 RPC 更简单可靠。硬上 MQ 不是免费午餐，是把简单问题复杂化。

## 四、扩展与分库（4 题）【第04篇】【第05篇】

**Q17. L4 和 L7 负载均衡有什么区别？** 【第04篇】
L4（传输层，代表 LVS/F5）只看 IP + 端口，像接线员一样转发 TCP 连接，不解析任何内容——因为不解包所以性能极高，LVS DR 模式回包不过负载器，单机扛百万级连接；代价是"瞎"，不知道请求是登录还是下单，无法按 URL 路由。L7（应用层，代表 Nginx/APISIX/Envoy）完整解析 HTTP，能按路径、Header、Cookie 路由，还能做限流、鉴权、灰度；代价是性能低一个数量级，自身也要集群化。经典结构是 L4 挡在 L7 前面；中小公司 DNS + L7（云 SLB + 自建 Nginx）足够。

**Q18. 一致性哈希解决什么问题？** 【第04篇】
解决"节点增减时大规模 key 重新映射"的问题：缓存集群用 hash(key) % N 定位，加一台机器 N 变 N+1，几乎全部 key 的取模结果都变，缓存大规模 miss、流量瞬间打穿 DB。一致性哈希把节点和 key 都映射到一个哈希环上，key 归顺时针最近的节点——加节点只"抢走"相邻节点的一小段弧，miss 率从几乎全部降到 1/(N+1) 量级；虚拟节点解决环上落点不均的负载倾斜。适用边界：缓存分片、分库分表这类"请求与存储位置强绑定"的场景；无状态 Web 应用用轮询或最少连接就够，上一致性哈希是过度设计。

**Q19. 什么时候该分库分表？** 【第05篇】
先给结论：分库分表是最后手段，不是性能优化的起点。驱动力只有三个：存储容量、连接数、写 QPS——读压力首选索引、缓存、读写分离，不是拆分。判断框架：读慢 → 索引优化/缓存/读写分离；表太大 → 冷热归档/分区表；连接数不够 → 连接池治理/垂直拆库；只有写 QPS 撞天花板才必须水平拆分。我自己的系统 400 万明细远没到拆的程度，月分区 + 冷热归档才是主线。再补一刀展示代价意识：拆完有六大后遗症——分布式事务、跨分片聚合、全局 ID、深分页、扩容迁移、运维爆炸。

**Q20. 分库分表之后分页查询怎么做？** 【第05篇】
先讲为什么痛：跨分片深分页是灾难升级版——取全局第 100 万页之后的 20 条，8 个分片要各自排序取出前 100 万+20 条，汇总 800 万行到中间层归并再截取，分片越多放大越狠。缓解三招：业务上禁止任意跳页，改游标式翻页（WHERE id > 上一页末尾 ID LIMIT 20），各分片只需各取 20 条；二次查询法，先各分片粗查确定全局边界，再按边界值精准二查，把归并量压到常数级；报表类复杂分页查询干脆不打分片库，同步到 ES/ClickHouse 查。

## 五、冗余与容灾（4 题）【第06篇】【第08篇】

**Q21. 主从复制延迟怎么解决？** 【第06篇】
先讲成因：大事务（从库串行回放整个事务能卡几十秒）、从库回放慢、从库被报表和备份任务打满抢不到资源。典型事故是"写完立刻读不到"的幽灵数据。解法不是四选一而是组合拳：默认读写分离扛流量 → 关键路径强制读主（用户改完资料的回显、凭证保存后的详情页）→ 半同步复制把丢失窗口压到接近 0（注意它保证"不丢"不保证"已回放"）→ 延迟监控降级（Seconds_Behind_Master 超阈值自动切回主库，全局兜底）。

**Q22. Redis 哨兵和 Cluster 的区别？** 【第06篇】
一句话：哨兵管"主挂了谁顶上"，Cluster 管"数据放不下了怎么办"。哨兵解决主从复制的自动故障切换：哨兵集群监控主库，挂了自动选从升主、通知客户端新地址；全量数据每个节点一份，容量上限是单机内存，复杂度低，中小团队首选。Cluster 解决数据超单机后的分片：16384 个 slot 分散到多个主节点，每个主带从库，可水平扩展；代价是跨 slot 的多 key 操作、事务、Lua 都受限。数据量不大却一上来上 Cluster，属于用大炮打蚊子。

**Q23. RPO 和 RTO 有什么区别？** 【第08篇】
RPO（恢复点目标）：灾难发生后最多允许丢失多长时间的数据，回答"数据回到哪个时间点"；RTO（恢复时间目标）：系统必须在多长时间内恢复服务，回答"用户要等多久"。关键认知：两个指标由业务定不由技术定——发票、对账流水丢了无法补录，RPO 趋近 0；行为日志丢一天没人疼。代价意识：RPO=0 意味着每笔写入都要等异地副本确认，跨城市 30ms 延迟直接写进每笔事务，吞吐和延迟显著恶化，所以"先让业务方在丢数据和停机之间签字画押，再谈技术方案"。

**Q24. 数据库被误删了怎么恢复？** 【第08篇】
标准原理是 PITR 时点恢复：全量备份是骨架，binlog 是血肉。步骤：找最近一次全量备份恢复到临时实例 → 从备份结束点的 binlog 位点开始回放，一路回放到 DELETE 执行前一秒 → 跳过那条事故 SQL（按 GTID 精确剔除），继续回放后续正常变更 → 校验后导回线上。配套认知两条：备份遵循 3-2-1 原则（3 份副本、2 种介质、1 份异地，勒索软件时代再加一份离线不可变）；没做过恢复演练的备份约等于没有备份——恢复演练才是容灾本体。

## 六、分布式（6 题）【第10篇】

**Q25. 讲讲 CAP？** 【第10篇】
先纠误读：CAP 不是"三选二"。C 是线性一致性（多副本对外表现像单副本，注意不是 ACID 的 C），A 是每次请求都能收到非错误响应，P 是分区容错。P 不可放弃——网络分区是"何时发生"不是"会不会发生"，所以真实选择只在分区那一刻：拒绝响应保 C 是 CP 系统，拿旧数据响应保 A 是 AP 系统；而在没有分区的 99.99% 时间里 CA 兼得。再补 PACELC：没分区时在延迟和一致性之间选，MySQL 半同步 vs 异步复制就是活例。案例收尾：注册中心该选 AP——地址簿旧一点有超时重试熔断兜底，注册中心自己挂了整个调用链瘫痪。

**Q26. 讲讲 BASE 理论？** 【第10篇】
BASE 是 AP 路线的工程化包装，三个词：基本可用（故障时允许损失部分可用性，功能降级但核心链路不死）、软状态（允许副本间存在暂时的中间态，这不是 bug）、最终一致性（没有新写入的前提下一段时间收敛，注意只承诺"最终"不承诺"多快"）。它不是推翻 ACID，而是承认跨机器强一致代价高到不可接受时，用"暂时不一致 + 事后收敛"换系统生存。落地手法：异步复制、消息驱动、对账补偿——我的对账系统就是最终一致性的业务版：我和银行之间没有任何分布式事务，靠对账文件事后比对收敛。

**Q27. 分布式锁怎么实现？Redlock 之争你怎么看？** 【第10篇】
主流是 Redis 锁，四个坑挨个过：加锁必须 SET NX PX 一条命令原子完成（拆两条会死锁）；过期时间是两难，解法是设远大于业务 P99 或 Redisson 看门狗续期；解锁前校验 value 里的唯一标识、用 Lua 原子删，防误删别人的锁；主从切换可能丢锁。Redlock 向 N 个独立节点抢锁、过半成功才持锁，但不绝对安全——Martin Kleppmann 与 antirez 之争的核心是时钟假设，GC 停顿、时钟跳变都会打破互斥。工程共识：效率场景（防任务双跑）够用；正确性场景（涉及钱）必须加 fencing token 或 DB 乐观锁/状态机兜底。

**Q28. 雪花算法的结构？时钟回拨怎么办？** 【第10篇】
64 位长整型：1 位符号位 + 41 位毫秒时间戳（约 69 年，高位是时间所以天然趋势递增）+ 10 位机器 ID（1024 节点）+ 12 位序列号（单机每毫秒 4096 个）。为什么要趋势递增：InnoDB 主键是聚簇索引，递增 ID 永远追加到 B+ 树最右端，随机主键（如 UUID）会引发页分裂。时钟回拨解法三档：回拨短就等待时钟追平；回拨长就拒绝服务 + 报警，宁可短暂不可用也不发重复号；工程方案（美团 Leaf、百度 UidGenerator）用 ZK 持久化机器 ID、发现回拨换机器 ID 重启发号器。

**Q29. 分布式 ID 有哪些方案？怎么选？** 【第10篇】
需求先摆四条：全局唯一、趋势递增（索引友好）、高可用、有时要可读带业务含义。四方案：UUID 无中心零依赖但太长无序，别当主键，适合 TraceID、临时 token；DB 自增 + 步长简单递增，但扩容要重设步长；号段模式批量从 DB 领号、DB 压力小、递增，订单号单据号的中厂主流；雪花算法本地生成性能极高，高并发场景大厂主流，坑是时钟回拨和机器 ID 管理。补一句业务视角：财务单据号不能纯随机——用"业务前缀 + 日期 + 序列"的结构化单号，可读可核对、带路由信息、不暴露业务量。

**Q30. 分布式事务有哪些方案？** 【第10篇】
地图式回答，按一致性强度分两路。强一致路：2PC——协调者先 prepare 全票通过再 commit，协调者单点 + prepare 阶段持锁阻塞，互联网高并发基本弃用；TCC——Try 预留资源、Confirm 确认、Cancel 释放，资金类强一致场景用，代价是业务侵入大、每个操作写三套逻辑。最终一致路：Saga——拆成一串本地事务、每步配补偿动作，适合长流程，补偿是业务语义回滚不是真回滚；本地消息表——本地事务顺手写消息表、后台轮询补发，最朴素无新中间件；RocketMQ 事务消息——半消息 + 回查，本地消息表的工业化版。收束：强一致花钱买确定性，最终一致用时间换吞吐；更优先的思路是用分片设计让事务退化成单库事务。

## 七、微服务与微前端（4 题）【第11篇】【第12篇】

**Q31. 什么时候该拆微服务？** 【第11篇】
先摆正认知：微服务解决的是组织问题不是性能问题——单体三大病（代码腐化互相踩踏、交付互相阻塞、技术栈锁死）都是随组织规模放大的，单体多实例 + 负载均衡通常比拆微服务更能扛量。触发拆分的信号：团队超过十人出现发布互相踩踏；某模块资源画像与其他模块显著不同、需要独立伸缩；组织上拆出了独立团队（康威定律反用）。反向判断同样重要，三条命中任一就别拆：团队小于 10 人、业务边界还在剧烈变动、没有专职运维和容器化监控基建。

**Q32. 微服务会带来哪些问题？** 【第11篇】
背"微服务税"清单五条：分布式事务——单体里一个 @Transactional 的事变成 Saga/TCC/最终一致消息，复杂度高一个量级；运维复杂度乘 N——10 个服务就是 10 条 CI/CD、10 套监控、10 份容量规划；测试复杂度——全链路联调昂贵脆弱，行业解法是契约测试；网络不确定性成为日常——超时、重试、部分失败，所有代码要按"对端可能不回答"来写；版本兼容与依赖地狱——字段只能加不能轻易删改，一次变更可能要多服务协调发布顺序。收束句：微服务不是架构的终点，是组织交付遇到瓶颈时才动用的手段，2026 年行业在向模块化单体理性回调。

**Q33. 微前端解决什么问题？** 【第12篇】
主战场只有一个：多团队维护的巨石前端——互相阻塞发布、技术栈绑架、构建变慢。本质是把微服务"独立开发、独立部署"的思想搬进浏览器，一个页面由多个团队的子应用在运行时或构建时拼装而成。和微服务对照着讲更显体系感：前端拆的是构建与团队边界，后端拆的是数据与可用性边界，两者是独立决策，谁也不依赖谁。反面判断：单人小项目上微前端是纯负资产——它买的是组织并行度，你没有并行需求就只剩成本。

**Q34. qiankun 的沙箱原理？和 Module Federation 怎么选？** 【第12篇】
沙箱两代演进：快照沙箱——mount 时遍历整个 window 拍快照，unmount 时 diff 还原，兼容性好（不依赖 Proxy）但全量遍历性能差、同一时刻只能一个子应用激活；代理沙箱——用 ES6 Proxy 给每个子应用造一个 fakeWindow，读全局先查假的再兜底查真的、写全局只写进假的，天然多实例、性能更好，代价是 Proxy 无法 polyfill。演进逻辑一句话："从兼容优先到隔离正确性优先"。再补一句边界：沙箱防的是无意工程污染，防不了恶意代码，强安全隔离回 iframe。选型（2026 标准答案）：新项目 Module Federation 2.0（构建期共享依赖、去中心化、Rspack 原生内置）；存量 qiankun 继续维护（已进维护期但存量巨大）；支付收银台、三方嵌入这类强隔离场景 iframe 依然是正解。

## 八、综合场景题（6 题）

**Q35. 设计一个秒杀系统，你会考虑哪些点？** 【第01篇】【第02篇】【第03篇】
按流量路径分层作答，六要点：
- **流量分层拦截**：商品页静态化走 CDN；前端按钮置灰 + 答题/验证码把峰值削掉一个量级；网关令牌桶限流，把绝大部分无效请求挡在应用之外。
- **库存前置**：库存预热到 Redis，用 Lua 原子预扣，只有扣成功的请求才放行——数据库直连必死（10 万人抢 5000 件，开抢瞬间估算约 8 万 QPS）。
- **削峰异步**：下单请求写进 MQ，后端按恒定能力匀速消费落库；前端给用户"排队中/已抢到/已售罄"三态，轮询或 WebSocket 推结果。
- **热点保护**：库存热 key 拆桶分摊单行竞争；缓存防击穿用逻辑过期。
- **防刷与兜底**：用户 ID + IP 双维度限购；超卖最后由 DB 兜底（库存不为负的条件更新、唯一约束）；熔断降级预案就位。
- **容量依据**：限流阈值和机器数从压测拐点打折推导，不是拍脑袋。

**Q36. 系统 RT 突然升高，你怎么排查？** 【第07篇】【第09篇】
- **先问变化**：最近有没有发布或配置变更——约七成生产事故由变更引发（经验口径，各家数字有出入），有则先回滚止血，恢复服务优先于定位根因。
- **分层看大盘**：入口 QPS 有没有突增（流量问题）；下游依赖的 RT（被下游拖慢）；自身资源水位——CPU、内存、GC、线程池、连接池（饱和度问题）。
- **沿调用链找"慢"**：链路追踪按 TraceID 定位慢在哪一跳；查慢查询日志和锁等待。
- **警惕"慢"而不是"错"**：下游不报错只是变慢时，线程池被占满层层传导，这正是雪崩前兆——该熔断熔断，别等它拖死全站。
- **收尾纪律**：止血后保留现场（摘一台问题实例、dump 日志），再从容排查根因。

**Q37. 你们系统的高可用是怎么做的？** 【第06篇】【第08篇】【第09篇】
用"沿链路讲"的叙事框架，而不是背方案清单：
- **单点狩猎开场**：画出请求链路，逐层问"这台挂了会怎样"——LB 主备、应用无状态多实例、数据库主从。
- **数据层**：MySQL 半同步复制（凭证不能丢）、读写分离 + 关键路径强制读主、Redis 哨兵自动切换；主动说清异步复制存在丢失窗口，展示诚实。
- **故障自愈**：所有远程调用显式超时、熔断降级 + 预案分级（P0 核心链路动不得、P1 可降级）。
- **容灾备份**：全量 + binlog 持续归档支持 PITR、备份按 3-2-1 原则、每季度真做一次恢复演练掐表。
- **变更管控**：业务敏感窗口不发版、金丝雀或简易蓝绿、数据库变更 expand-contract、可回滚是发布前提。
- **收尾点题**：高可用的本质是按业务停机成本配置冗余，不是堆方案——先算"停机一小时损失多少钱"。

**Q38. 日活百万的系统，QPS 怎么估？** 【第00篇】
固定三步法：日活 → 高峰集中系数 → 人均请求数。
- 人均请求：假设人均 50 次接口调用（刷 feed、点赞、加载评论），日总请求 = 100 万 × 50 = 5000 万次。
- 平均 QPS = 5000 万 ÷ 8.6 万秒 ≈ 580（日均 8 万秒可近似 10 万秒口算）。
- 峰值 QPS = 均值 × 高峰集中系数（取 5，流量集中在 20% 时间）≈ 3000。
- **估完立刻给方案判断才算完整**：3000 QPS 量级，小集群 + Redis + 读写分离可扛，谈分库分表属于过度设计；再补一句"若其中混着扫百万行的重型查询，要单独做资源隔离"——数字感 + 方案判断，是这道题的全分结构。

**Q39. 灰度发布怎么做？发布失败怎么回滚？** 【第09篇】
- **灰度节奏**：内部白名单 → 按用户 ID 哈希切 1% → 10% → 50% → 100%，每档设观察期，盯三个黄金指标：错误率、P95/P99 RT、业务量（业务量骤降可能比错误率更早暴露问题）。实现上记住一句：打标在入口，路由在网关。
- **策略选择**：无状态服务默认滚动发布（零额外资源，但 API 和数据库必须前后兼容）；核心链路变更叠加金丝雀；要秒级回滚且有闲置资源用蓝绿。
- **回滚的前提**：可回滚必须在发布之前就成立——数据库变更用扩展-收缩模式（先加不删，删是下一次发布的事），否则"回滚了，又没完全回滚"。
- **事故纪律**：先回滚/切流止血 → 保留现场 → 再排查。恢复服务永远优先于定位根因。

**Q40. 单机和微服务怎么选？** 【第13篇】
用五步叙事框架组织回答：现状约束 → 驱动变化的因素 → 候选方案 → 取舍理由（必须挂回第一步的约束）→ 止损回退预案。
回答骨架：判断维度有三个——团队规模（微服务的人均运维成本小团队喂不起）、交付冲突是否是真实瓶颈（微服务解决的是这个，不是性能）、一致性要求（财务系统一致性优先，分布式事务的代价最大）。我的约束下三个维度都指向模块化单体；同时我把模块边界、幂等、全局 ID 都按可拆分标准做了，触发拆分的信号是明确的——比如对账模块出现独立的伸缩需求或独立的发布节奏。加分收尾：能讲清楚"为什么在简单处停下"，比堆砌复杂方案高一个段位——约束下的克制是稀缺品质。
